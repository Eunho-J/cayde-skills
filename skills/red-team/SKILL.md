# 레드팀

설계에서 지켜야 할 상황과 기대 결과를 먼저 확정하고, 테스트와 독립 검토를 그 목록에 연결한다. 반드시 **1차 설계 분석 → 2차 테스트·보완 → 3차 항목별 독립 검토** 순서로 진행한다. 발견한 결함 수나 테스트 총수를 종료 기준으로 쓰지 않는다.
**레드팀은 구현 단위로 테스트할 수 있는 항목만 다룬다. 모든 테스트는 입출력과 프로그램의 변수값 변화만으로 수행한다.** 함수·모듈에 실제 입력을 주고 반환값·출력 및 실행 전후 변수값을 비교한다. 여기서 상태는 프로그래밍 언어의 변수이며, 객체 필드·자료구조의 값도 이에 포함된다. 실제 사용자·서비스·계정이 필요한 실사용 시험은 레드팀 목록과 완료 기준에서 제외하고 사용자 수행 항목으로 따로 안내한다.

## 작업 경계와 기록

- 최신 사용자 결정·정정과 해당 설계 문서를 기준으로 삼는다. 후보·질문·철회된 제안을 필수 요구로 바꾸지 않는다.
- 사용자가 지정한 범위와 기존 권한을 따른다. 이 절차의 실행 요청에는 범위 안의 테스트 추가와 발견한 구현 결함 보완이 포함된다. 사용자가 읽기 전용·검토만을 지정했으면 그 제한을 지키고 수정할 항목을 기록한다. 스킬을 만드는 요청만으로 대상 제품의 레드팀을 시작하지 않는다.
- 프로젝트의 문서 관례에 맞춰 `<topic>/edge-cases.md`를 별도 파일로 관리한다. 정해진 위치가 없으면 `.codex/red-team/<topic>/edge-cases.md`를 사용한다. [목록 양식](assets/edge-cases.template.md)을 복사해 시작한다.
- 설계에서 도출한 사례와 테스트·구현·검토 증거를 구별한다. 각 사례에 고정 ID를 부여하고, 기대 결과를 테스트 통과에 맞춰 조용히 바꾸거나 실패 항목을 삭제하지 않는다.
- 코드 기준 버전과 변경 후 버전을 기록한다. 수정한 코드에서 기존 검토의 근거가 달라졌다면 영향을 받는 사례의 검토 상태를 다시 연다. 사용자 목표의 완료 여부와 이번 목록의 검증 완료를 별도로 판단한다.

## 테스트 실행 경계

- **테스트는 프로젝트의 표준 테스트 코드·테스트 스크립트와 테스트 러너 안에서만 작성·실행한다.** 기존 `cargo test`, `pytest`, `npm test` 등의 실행 경로에 사례와 assertion을 추가한다. 테스트가 부족하다는 이유로 독자적인 검증 시스템을 만들지 않는다.
- **모든 테스트의 검증 대상은 구현의 입출력과 변수값 변화뿐이다.** 유닛·통합·회귀 등 테스트의 이름을 바꿔 다른 검증을 허용하지 않는다. 파일 존재·권한·inode, 프로세스 생존·PID, 서비스·외부 앱·컴퓨터 상태, 소스 구조를 변수 상태 대신 검사하지 않는다. 그런 외부 상태를 읽어 변수에 담았다는 이유로 허용되는 변수 검증이라고 취급하지 않는다.
- **유닛테스트에서 정규식 사용을 금지한다.** 테스트 본문·assertion·테스트 도우미에서 정규식으로 텍스트를 검출하거나 기대 결과를 판정하지 않는다. `assertRaisesRegex` 같은 정규식 assertion도 사용하지 않는다.
- **제품 소스의 텍스트·코드 스니펫·코드 존재 여부를 확인하는 가짜 테스트를 작성하거나 유지하지 않는다.** 소스 파일을 읽어 정규식·문자열 검색·AST 노드 존재 검사만 하는 것으로 구현 동작 검증을 대신하지 않는다. 정규식을 `contains`나 다른 검색 방식으로 바꿔 같은 검사를 남기는 것도 금지한다. 실제 구현 함수가 반환한 문자열·오류 값을 비교하는 출력 검증은 소스 존재 검사와 구분한다.
- **별도 외부 검증 프로그램·실행파일·상주 프로세스를 만들거나 사용하지 않는다.** 시험용 실행기, 컨트롤러, 수집기, 원격 실행·전송 프로그램, 증거 수집 서비스, 컴퓨터·브라우저·OS를 조작하는 시험기를 금지한다. 예제 바이너리나 다른 이름의 테스트 스크립트로 포장해도 같은 금지 대상이다.
- 표준 테스트 스크립트에서 기존 외부 컨트롤러·컴퓨터 조작 도구를 호출하는 방식으로 이 금지를 우회하지 않는다.
- 표준 테스트 러너 자체의 프로세스 실행은 허용된다. 임시 fixture와 정리는 러너가 관리하는 프로젝트 테스트 코드 안에 한정한다. 이를 별도 프로세스로 운영 봇·서비스·원격 호스트·컴퓨터 UI를 조작하는 시험기로 확장하지 않는다.
- 구현 단위의 유닛테스트로 확인할 수 없는 실제 통합·실사용 경계는 레드팀 대상에서 제외하고 이유를 기록한다. 목록을 전부 통과시키려고 외부 시험기를 새로 만들거나 이미 만든 것을 재사용하지 않는다.
- **실사용 시험은 사용자만 수행하며, 에이전트는 수행하지 않는다.** 음성 발화·청취·음성 채널 대화, 실제 Discord 메시지·폼·승인 버튼 조작, 실제 계정과 운영 환경에서 제품을 사용하는 시험이 이에 포함된다. 에이전트의 직접 조작, UI 자동화, 별도 프로그램, 서브에이전트 위임 모두 금지한다. 일반적인 “테스트해”, “E2E 확인해” 요청을 에이전트의 실사용 수행 허가로 해석하지 않는다.
- 에이전트는 별도 사용자 수행 목록에 실사용 시험의 최소 절차와 기대 결과를 안내하고, 사용자가 전달한 결과를 기록·분석하며 필요한 코드와 표준 테스트를 보완한다. 사용자 결과가 오기 전에는 그 별도 목록에 `blocked: user_validation_required`로 남긴다. 에이전트의 소스 검토나 유닛테스트 결과를 실사용 통과로 바꾸지 않는다.
- 항목별 독립 검토의 순서는 대화와 목록 문서로 관리한다. 검토 큐·배정·재시도·결과 수집을 위해 별도 실행 프로그램을 만들지 않는다. 이 경계는 주 담당자와 모든 서브에이전트에 동일하게 적용한다.

## 1차: 코드 없이 설계의 엣지 케이스를 작성한다

### 읽을 자료와 완료 조건

1. 설계 문서·확정된 사용자 발언·목표·비목표·설계 제약만 읽는다. 구현 소스, 테스트 소스, 실행 결과, 구현에서 도출한 감사 보고서·구현 계약을 사례 도출의 근거로 읽지 않는다. 파일 위치와 작업 지침은 확인할 수 있지만, 그 과정에서도 제품 코드·테스트 내용을 열지 않는다.
2. 현재 세션에 이미 구현 정보가 있으면 **설계만 전달한 격리된 작성자**에게 1차를 맡긴다. 가능하면 `fork_turns="none"`으로 생성하고 설계 자료 경로와 작성 권한만 준다. 기존 코드 검토자나 전체 대화 이력을 그대로 재사용하지 않는다. 격리가 불가능하면 코드에서 독립적으로 작성했다는 주장을 하지 않고 제한을 기록한다.
3. 설계 의무 중 구현 단위로 테스트할 수 있는 범위를 먼저 정하고, 그 범위에서 정상 상황, 경계 상황, 실패 상황, 다른 의무와 함께 적용되는 상황을 도출한다. 설계에 있는 값·동작·수명·입출력·식별·동시성·재시도·단계 간 관계를 교차 검토한다. 실사용이 필요한 의무와 관련 없는 축은 제외 이유를 기록한다. 모든 프로젝트에 특정 자료형·GC·호환성·성능 보장을 강요하지 않는다.
4. 단독 기능 외에도 설계가 약속한 관계를 사례로 만든다. 예를 들어 같은 대상을 표현하는 두 방법의 의미 일치, 앞 단계에서 허용한 자료의 뒷 단계 처리, 실패 뒤 재시도와 수명 경계처럼 여러 기능을 통과하는 상황을 살핀다. 코드 구조나 이전 결함 이름에서 사례를 역산하지 않는다.
5. 각 사례에 **설계 근거, 선행 조건, 구체적 입력·행동 순서, 기대 결과, 반드시 보존될 것, 정상 대조, 적용 범위**를 적는다. 상태 변화나 오류·허용 여부를 관찰할 수 있어야 한다. 구현 함수명이나 알고리즘을 정답으로 넣지 않는다.
6. 설계의 구멍은 결정된 의무를 동시에 만족시킬 수 없는 상황, 또는 기대 결과를 정할 필수 규칙이 빠진 상황으로 제시한다. 최소 상황과 영향·누락된 규칙을 설명한다. 선택 가능한 구현 방식이 남아 있다는 이유만으로 구멍으로 세지 않는다. 기대 결과가 미정인 항목은 `design_pending`으로 남기고 임의 정책을 만들지 않는다.
7. 설계 의무별로 사례 ID를 연결하고 누락·겹침을 확인한다. 같은 원인의 반복을 정리하되 서로 다른 입력 경로나 기대 결과를 지우지 않는다. `edge-cases.md`에 설계 기준과 목록 버전을 기록해 1차를 완료한 뒤에만 코드·테스트를 읽는다.

### 1차 문서의 작성·검수 규칙

다음 규칙을 이 스킬 자체에서 적용한다.

- 문서의 목적은 다음 담당자가 설계의 어떤 의무를 어떤 상황에서 검증해야 하는지 이해하게 하는 것이다. 원 설계를 모르는 검토자가 필요한 관계를 복원할 수 있도록 쓴다.
- 먼저 목표·경계·설계 의무를 설명하고, 그 의무에서 도출되는 상황과 기대 결과를 연결한다. 자료를 읽은 순서나 조사자별 결과를 목차로 옮기지 않는다.
- 사례는 같은 설계 의무·관계를 기준으로 묶는다. 각 묶음이 답하는 질문과 다음 묶음이 필요한 이유를 분명히 하고, 자료의 분류명만으로 섹션을 만들지 않는다.
- 한국어 본문은 완전한 문장으로 쓴다. 표의 짧은 이름만으로 처리 내용을 대신하지 않는다. 주체·대상·조건·처리·판정 기준·결과 중 이해에 필요한 관계를 적는다.
- “수명을 관리한다”, “오류를 처리한다”, “원자성을 보장한다”로 설명을 끝내지 않는다. 누가 언제 무엇을 보관·변경·거부하며, 어떤 값과 진행 위치가 유지되는지 구체적으로 쓴다.
- 문단은 앞 문단의 대상이나 질문을 이어받아 조건·행동·결과·이유를 발전시킨다. 대상과 평가 기준이 바뀌면 이동에 필요한 전제를 설명한다. 접속어만 추가해 논리의 비약을 감추지 않는다.
- 설계에 명시된 사실, 그 사실에서 도출한 사례, 작성자의 해석·제안·미정 규칙을 구별한다. 원문·출처·합의·실험 결과를 지어내지 않는다. 근거가 부족하면 `[설계 근거 필요]`로 표시하거나 주장의 범위를 줄인다.
- 자료는 어떤 기대 결과를 뒷받침하는지 설명할 수 있을 때 사용한다. 관련 있다는 이유로 내용을 전부 복사하지 않는다. 목록 전체를 작성하라는 범위는 충족하면서 불필요한 배경·반복·곁가지는 덜어낸다.
- 반증과 기대 결과의 성립 조건을 남긴다. 제약이나 예외를 생략해 필수 요구처럼 보이게 만들지 않는다. 관계없는 가상 위험을 끼워 넣어 사례 수를 늘리지 않는다.
- 문단마다 실제 역할을 한 줄로 적는 역개요로 검수한다. 시작과 끝을 이어 읽어 필요한 설명이 누적되는지 확인하고, 문단·섹션을 빼 보아 중복이나 역할 없는 부분을 삭제한다. 삭제하면서 필수 사례·반증·조건이 사라지지 않게 한다.
- 문장이 자연스러워도 입력·행동·기대 결과를 설명할 수 없으면 다시 쓴다. 상위 구조의 문제는 표현만 매끄럽게 고쳐 덮지 않고 구성부터 수정한다. 본문에 작성 과정의 대화나 검수 메모를 그대로 옮기지 않는다.
- 보고서는 검증하는 대상과 사건을 주어로 쓴다. “나·우리”의 작업 감상 대신 관찰할 상황과 판단 근거를 설명한다. 중요한 수정이 반영되면 영향을 받은 앞뒤와 전체 목록을 다시 읽는다.

## 2차: 각 사례의 유닛테스트를 확인하고 보완한다

1. 이제 구현·테스트·빌드 규칙을 읽는다. 목록의 각 ID에 상응하는 테스트의 파일·이름·실제 assertion을 연결한다. 비슷한 테스트 제목이나 테스트 개수만으로 대응한다고 판정하지 않는다.
2. 테스트가 해당 구현 단위에 실제 입력을 주고 출력과 실행 전후 변수값만 검사하는지 확인한다. 보존 조건도 유지되어야 할 변수값으로 확인한다. 정상 경로만 검사하거나 같은 구현을 기대값 계산에 재사용하면 충분한 대응 테스트가 아니다. 정규식 사용, 제품 소스·코드 존재 검사, 파일·프로세스·서비스 등 외부 상태 검사로 대신하는 테스트는 삭제한다.
3. 없거나 부족하면 **프로젝트의 표준 테스트 코드·스크립트에 실패를 관찰할 수 있는 테스트를 먼저 추가·실행**한다. 설계의 기대 결과를 기준으로 판정하며 동작을 그대로 복사한 기대값을 만들지 않는다. 기존 테스트도 실행하지 않고 통과로 표시하지 않는다. 별도 실행기·외부 검증 도구를 만들거나 사용하는 것으로 대체하지 않는다.
4. 실패한 사례를 최소 재현으로 확인하고 범위 안의 구현 결함을 수정한다. 테스트의 기대값을 약화해 녹색으로 만들지 않는다. 수정한 항목과 같은 설계 규칙을 사용하는 다른 입력·출력·수명 경로도 대조한다.
5. 수정 후 해당 구현 단위의 테스트와 영향을 받는 회귀 테스트를 표준 러너로 실행하고 명령·종료 상태·로그·코드 버전을 기록한다. 실행할 수 없는 단위 테스트는 `blocked`로 남기며 별도 시험기를 제작하지 않는다. 실제 계정·운영 환경을 사용하는 시험은 레드팀 밖의 사용자 수행 항목으로 남긴다.
6. 목록의 모든 항목을 확인한다. 미정 설계·권한 제한·환경 부재는 `blocked`로 남기고 이유를 적는다. 다음 항목을 처리할 수 있으면 계속한다. 주요 설계 모순은 영향과 최소 사례를 보고하며 관련 구현을 멈춘다. 통상 구현 오류는 보완하면서 진행한다.
7. 각 항목의 테스트 상태와 증거를 기록한 뒤 3차로 넘어간다. 미해결 항목은 목록에 남겨 독립 검토에도 전달하며 성공으로 간주하지 않는다.

## 3차: 서브에이전트에게 한 항목씩 전달한다

### 배정 규칙

- 독립 검토자를 생성하고 공통 설계 기준·대상·버전·읽기 전용 권한만 먼저 전달한다. 인원은 범위와 가용성에 맞추되 사용자가 지정한 인원은 따른다. 동일 검토자를 다음 항목에도 재사용할 수 있다.
- 처음부터 전체 목록·여러 항목·조사 영역 전체를 주며 “조사해줘”라고 요청하지 않는다. 가능하면 `fork_turns="none"`을 사용하고 전체 대화나 이전 담당자의 결론을 자동으로 넘기지 않는다.
- **전체 루프의 active 항목은 하나다.** 검토자가 여럿이면 모두 같은 active 항목을 검토한다. 다음 항목을 다른 검토자에게 미리 보내는 병렬 배치도 하지 않는다. 현재 항목 안에서 독립 검토를 병렬화할 수 있다.
- 주 담당자가 목록에서 현재 항목만 발췌해 전달한다. 전체 목록 경로를 읽도록 지시하지 않는다. 설계 근거·선행 조건·입력·행동·기대 결과·정상 대조·현재 코드 버전을 전달하되, 담당자의 의심 원인·추천 수정·정답·이미 통과했다는 결론은 먼저 주지 않는다.
- [항목별 지시 형식](references/single-case-review.md)을 사용한다. 구현과 테스트를 보고 이 상황에서 설계 의무가 깨질 염려가 있는지 검토하게 한다. 실제 근거·반례·정상 대조를 요구하며 “문제 없어 보임”만으로 끝내지 않게 한다.
- 모든 배정에 구현 단위의 표준 유닛테스트만 허용하고 정규식·소스 존재 검사·별도 외부 시험기는 금지하며, 실사용 시험은 사용자만 수행한다는 경계를 함께 전달한다.

### 반복 절차

```text
목록의 미검토 항목을 정해진 순서로 선택한다.
  현재 항목 하나를 검토자에게 전달한다.
  검토 결과와 근거를 기다린다.
  주 담당자가 설계·코드·테스트·재현을 대조한다.
  근거가 부족하면 현재 항목만 더 구체적으로 다시 검토시킨다.
  결함이 있으면 테스트를 보완하고 수정·실행한 뒤
    같은 항목을 변경된 버전에서 다시 검토시킨다.
  판정·증거·버전을 기록하고 현재 항목을 마무리한다.
  그 후에만 다음 항목 하나를 전달한다.
목록의 모든 항목을 처리할 때까지 반복한다.
```

보고를 그대로 복사하거나 다수결로 판정하지 않는다. 테스트가 통과해도 assertion 누락·검증 경계 차이·관련 경로의 반례가 있는지 살핀다. 구현 결함, 설계 미정, 미검증을 구별한다. 권한·환경·설계 미정으로 끝내 검증할 수 없는 항목은 `blocked`로 명시한 후 다음 항목을 검토하며, 전체 완료 판정에서는 제외한다.

수정으로 이전 항목의 근거가 달라지면 그 항목을 `needs_recheck`로 돌려 순차 큐에 다시 넣는다. 새 사례가 발견되면 해당 설계 의무로부터 도출되는지 확인하고 기존 항목의 변형인지 구별한다. 추가 설계 분석은 구현 정보 없는 작성자에게 설계 자료만 전달해 보완시키고, 추가·변경한 사례도 2차 테스트 보완을 거쳐 3차 큐에서 하나씩 검토한다. 설계 변경과 목록 변경 이력을 남긴다.

서브에이전트 도구가 없거나 호출이 실패하면 그 항목을 독립 검토 통과로 표시하지 않는다. 가능한 표준 테스트·소스 검토를 수행하고 남은 독립 검토를 보고한다. 실사용 시험을 에이전트의 직접 확인으로 대체하지 않는다.

## 종료와 사용자 보고

- 선언한 설계 의무에 사례가 연결되고, 각 active 사례에 실행한 대응 테스트와 현재 버전의 독립 검토가 있어야 목록의 검증을 완료할 수 있다.
- `design_pending`, 실패, `blocked`, 미검토, `needs_recheck`가 남으면 **부분 검증**이다. 제약과 남은 항목을 정확히 보고한다. 제외 항목은 원 설계·범위 근거가 있어야 하며 조용히 삭제하지 않는다.
- 실행하지 않은 검사, 다른 버전·SDK의 이전 실행, 수정 전 결과를 현재 통과의 근거로 사용하지 않는다. 확인한 유한 범위를 모든 입력·경로·경합의 무결함 증명으로 확대하지 않는다.
- 별도 파일 위치, 사례 총수와 상태별 수, 발견·보완 사항, 명령·근거, 미검증·미결정을 간결하게 보고한다. 내부 배정 메시지를 반복해서 사용자에게 나열하지 않는다.
- 레드팀 목록을 모두 검사한 사실만으로 전체 제품 목표를 완료 처리하지 않는다. 제품의 나머지 완료 기준과 알려진 미완료 사항을 함께 확인한다.
