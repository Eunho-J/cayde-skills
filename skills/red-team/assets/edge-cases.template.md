## 사례 목록

### EC-001. {{상황을 설명하는 이름}}

- **설계 근거:** 어떤 원문 의무에서 이 사례가 도출되는지 적는다.
- **필수 여부:** `required` / `design_pending` / `excluded_with_reason`.
- **선행 조건:** 주체·대상·상태·호출 단계가 어떤 상황인지 적는다.
- **입력과 행동 순서:** 실제 검증자가 재현할 수 있게 서술한다.
- **기대 결과:** 허용·거부·변경·반환·종료를 관찰 가능한 문장으로 적는다.
- **보존 조건:** 실패나 단계 전환 후에도 유지되어야 할 값·위치·소유 등이 있으면 적는다.
- **정상 대조와 적용 범위:** 정상 사례와 이 항목이 다루는 입력·경계·변형을 적는다.
- **미정 규칙:** 기대 결과를 확정할 수 없다면 부족한 규칙과 영향을 적는다.

이 블록을 설계에서 도출한 사례 수만큼 복사한다. 항목별로 실제 내용을 작성하며 예시 문구를 완성된 사례로 취급하지 않는다.

## 2차 테스트 대응과 보완

| 사례 ID | 테스트 파일·이름과 검사하는 assertion | 상태 | 실행 명령·결과·로그 | 수정 전·후 코드 버전 | 관련 경로 보완 |
|---|---|---|---|---|---|

상태는 `pending`, `missing`, `failing`, `passed`, `blocked`로 구별한다. 테스트 이름만 적지 않고 사례의 어떤 기대 결과와 보존 조건을 검사하는지 설명한다.
테스트 파일과 명령은 프로젝트의 표준 유닛테스트 코드·스크립트 및 러너를 가리켜야 한다. 유닛테스트의 정규식 사용과 제품 소스의 텍스트·코드 스니펫·코드 존재 검출을 금지한다. 별도 외부 시험기·실행기·수집기를 만들거나 사용하지 않는다.
모든 테스트는 입출력과 프로그램 변수값 변화만 검사한다. 상태는 객체 필드·자료구조를 포함한 언어의 변수이며, 파일·프로세스·서비스·컴퓨터의 외부 상태나 코드 구조를 뜻하지 않는다.
음성 등 실사용 시험은 레드팀 대상에서 제외하고 사용자만 수행한다. 에이전트는 직접 조작이나 자동화로 대신하지 않으며, 별도 사용자 수행 목록에서 결과가 없으면 `blocked: user_validation_required`로 기록한다. 레드팀 단위 테스트 결과와 사용자 실사용 결과를 구별한다.
